# 饭点外卖推荐 PWA — 设计文档

日期：2026-08-22
状态：已评审，待写实现计划

## 1. 背景与目标

每天三个饭点都要重新决定「吃什么」，这个决策成本高、重复、且结果往往不如意。本项目的目标是**消除这个决策**：到饭点时，手机自动打开一张卡片，上面只有一个选择，点一下就跳到外卖 App 完成下单。

推荐要同时照顾三个维度：干净、经济实惠、美味。

**成功标准**：连续使用一个月后，超过一半的饭点是直接点了推荐去下单的（而不是按「换一个」或关掉页面自己去搜）。

## 2. 非目标（v1 明确不做）

- 多用户、账号体系
- 营养、卡路里
- 消费统计报表
- 菜品图片
- 天气、心情等上下文因子
- 任何形式的外卖平台数据抓取
- Service Worker 与离线能力
- Web Push

## 3. 关键决策

### 3.1 不代替用户下单

美团和饿了么没有面向个人开发者的公开下单 API，其开放平台只对商家/服务商开放。模拟登录或手机自动化（Appium 一类）违反平台用户协议且极其脆弱。

**决策**：程序只负责推荐并提供跳转链接，最后的下单和支付由用户在外卖 App 内自己完成。分享链接并跳转是平台自身提供的能力，属于正常使用。

### 3.2 不抓取平台数据

**决策**：自建候选池 —— 用户手动录入常吃/想吃的店和菜；每次真实下单后回录反馈，推荐质量随使用时间提升。零爬虫、零反爬对抗、零合规风险。

代价是冷启动需要用户先录入 20–30 家店。这是本项目最大的一次性投入。

### 3.3 形态为 PWA，不做微信小程序

微信小程序的 `wx.navigateToMiniProgram` 要求目标小程序把调用方 AppID 加入跳转白名单，个人开发者无法获得；跳转外链也会被微信拦截。微信小程序恰好卡在本产品最核心的「一键跳过去下单」这一步。

**决策**：做手机网页（PWA），添加到 iPhone 主屏。

### 3.4 零后端

**决策**：无服务器、无数据库、无构建步骤。数据全部存于手机本地 IndexedDB。定时唤起用 iOS 快捷指令的个人自动化，不用推送通道。

理由：这是单人自用工具，真正的成本是用户手动录入候选池并坚持回录三个月，而非技术实现。任何运维负担都在提高半途而废的概率。备份需求由「一键导出 JSON」覆盖。

升级路径：数据模型与推荐逻辑与「有后端」的方案完全一致。将来若要加服务端，只需替换存储层，前端不动。

### 3.5 不用 Service Worker

iOS 从不要求 Service Worker 才能「添加到主屏幕」，`display: standalone` 的 manifest 即可；Safari ITP 对脚本可写存储的 7 天清理规则，其豁免条件是「已安装到主屏」，与是否有 SW 无关。

**决策**：v1 只放 manifest，不注册 Service Worker。SW 只换来离线能力，代价是 iPhone 上最难排查的缓存问题。

已知后果：弱网时页面打不开；iOS Web Push 强制依赖 SW，因此该路线在 v1 关闭。

### 3.6 每顿只给一个推荐

给三个并排选择只是把纠结从 50 个店缩小到 3 个，没有真正消除它。

**决策**：一顿一个推荐，配一个「换一个」按钮，上限 2 次，用满后按钮消失。被换掉的选项计为负反馈。

## 4. 架构

**技术栈**：原生 HTML + CSS + JavaScript，无构建步骤。存储 IndexedDB。托管于 GitHub Pages（PWA 需要 HTTPS）。无 npm 依赖。

**四个模块**：

| 模块 | 职责 | 依赖 |
|---|---|---|
| `store` | IndexedDB 读写、导出/导入 JSON | 无 |
| `recommender` | 输入候选池 + 事件历史 + 饭点，输出一个推荐及理由 | 纯函数，不碰 DOM 和存储 |
| `ui` | 页面渲染与交互 | `store`、`recommender` |
| `deeplink` | 生成跳转链接、记录点击、兜底复制 | 无 |

`recommender` 必须是纯函数：推荐逻辑是最需要反复调整的部分，做成纯函数才能脱离浏览器充分测试。

**仓库公开无隐私问题**：代码中不含任何用户数据，候选池与用餐记录仅存于手机本地，从不上传。

## 5. 数据模型

三个 object store。

### 5.1 `shops`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 主键 |
| `name` | string | 店名 |
| `platform` | `'meituan' \| 'eleme'` | 平台 |
| `link` | string | 从外卖 App 分享出来的 H5 短链 |
| `hygiene` | `'unknown' \| 'trusted' \| 'blocked'` | 卫生标记，默认 `unknown` |
| `note` | string | 备注，可空 |

### 5.2 `dishes`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 主键 |
| `shopId` | string | 外键 → `shops.id` |
| `name` | string | 菜名 |
| `refPrice` | number | 参考价（元） |
| `tags` | string[] | 菜系、辣度、主食类型等 |
| `slots` | `('breakfast' \| 'lunch' \| 'dinner')[]` | 适用饭点，可多选 |
| `active` | boolean | 是否启用 |

粒度定在**菜品**而非店铺：「今天吃黄焖鸡」比「今天吃 XX 家」更能消灭纠结，且同一家店不同菜的好吃程度差别很大。跳转链接挂在店铺上，同店所有菜共用。

### 5.3 `events`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 主键 |
| `ts` | number | 时间戳（毫秒） |
| `slot` | `'breakfast' \| 'lunch' \| 'dinner'` | 饭点 |
| `dishId` | string | 外键 → `dishes.id` |
| `type` | 见下 | 事件类型 |
| `value` | number \| string \| null | 见下 |

`type` 取值与 `value` 语义：

| `type` | `value` | 何时写入 |
|---|---|---|
| `recommended` | `null` | 每次向用户展示一个推荐时 |
| `swapped` | `null` | 用户按「换一个」时 |
| `clicked` | `null` | 用户按「去下单」时 |
| `rated` | `'good' \| 'ok' \| 'bad' \| 'skipped'` | 用户在反馈浮层打分时 |
| `paid` | number（元） | 用户填写实付价时 |
| `sick` | `null` | 用户点「吃坏了」时（同时将该店 `hygiene` 置为 `blocked`） |

**只存事件流，不存聚合分数。** 这样「推了但既没点也没换」本身就是一条可分析的记录，同时评分公式可以随时修改并对全部历史重算。

## 6. 推荐算法

`recommender` 是纯函数：

```
recommend({ dishes, shops, events, slot, now, excludedDishIds }) -> { dish, reason } | null
```

### 6.1 硬过滤

依次剔除：

1. 所属店铺 `hygiene === 'blocked'`
2. `dish.active === false`
3. `!dish.slots.includes(slot)`
4. `dish.id ∈ excludedDishIds`（本顿已被换掉的）

过滤后为空则返回 `null`，UI 显示引导用户去候选池添加菜品。

### 6.2 从事件流归约出观察值

以一次 `recommended` 事件为起点，**同一本地日期、同一 `slot`、同一 `dishId`** 的后续事件构成一个 observation。所有日期与「天数差」的计算一律按设备本地时区取自然日。归约按优先级取第一个命中的：

1. 存在 `rated` → 用其映射值
2. 否则存在 `swapped` → `0.2`
3. 否则存在 `clicked` → `0.65`
4. 否则（推了但无任何动作）→ `0.45`

`rated` 的映射：

| `value` | 观察值 |
|---|---|
| `good` | 1.0 |
| `ok` | 0.5 |
| `bad` | 0.0 |
| `skipped`（没吃成） | 0.4 |

`skipped` 的存在是为了修正 `clicked` 的 `0.65`：用户可能点了跳转但被配送费或评价劝退。有了显式的「没吃成」，这条信号才不会被错误地记成「他想吃」。

### 6.3 好吃度 `taste ∈ [0,1]`

对该菜的全部 observation 做**时间加权平均**，半衰期 `TASTE_HALFLIFE_DAYS = 60`：

```
w_i    = 0.5 ^ (daysAgo_i / 60)
taste  = Σ(w_i · v_i) / Σ(w_i)
```

**冷启动用乐观初始化**：无任何 observation 的菜，`taste = COLD_START_TASTE = 0.7`（高于平均）。新录入的菜因此会被优先推出来试，试过后自然回落到真实水平。这是最省事的探索机制，无需引入 bandit 算法。

半衰期 60 天的理由：口味会变，一年前的评价不该与上周的等权。

### 6.4 实惠度 `value ∈ [0,1]`

`effectivePrice = 最近一次 paid 事件的值 ?? dish.refPrice`

在**当前 slot 的过滤后候选集**中计算该价格的百分位 `p ∈ [0,1]`（0 = 最便宜），则 `value = 1 - p`。

候选集只有一个元素时，`value = 0.5`。

用百分位而非绝对值：用户永远不必定义「多少钱算便宜」，它自动适应其消费水平。

### 6.5 腻味系数 `fatigue ∈ (0,1]`

三个乘性衰减，全部基于「真的吃了」的日期（即 `rated` 为 `good`/`ok`/`bad` 的事件；`skipped` 不算吃过）：

```
f_dish = 1 - exp(-d_dish / 7)        // d_dish = 距上次吃这道菜的天数
f_shop = 1 - 0.5 · exp(-d_shop / 3)  // 距上次吃这家店的天数，惩罚上限 50%
f_tag  = 1 - 0.3 · exp(-d_tag  / 2)  // 距上次吃同 tag 的天数，惩罚上限 30%
                                      // 多 tag 取最小值（最近吃过的那个 tag 说了算）

fatigue = max(0.02, f_dish · f_shop · f_tag)
```

从未吃过的，对应因子取 `1.0`。下限 `0.02` 用于避免乘零导致理由生成时除零。

`f_dish` 的手感：3 天前吃过 → 0.35，7 天 → 0.63，14 天 → 0.86，30 天 → 0.99。

`f_shop` 与 `f_tag` 的作用是防止连着三顿都是川菜或都来自同一家店。

### 6.6 最终评分

```
score = (0.7 · taste + 0.3 · value) · fatigue · jitter
jitter ~ Uniform(0.85, 1.15)
```

取 `score` 最高者。`jitter` 保证数据稳定后也不会天天推同一道菜。

### 6.7 常数集中管理

以上全部常数写在一个 `CONFIG` 对象中，便于后续凭使用体感直接修改：

```js
const CONFIG = {
  W_TASTE: 0.7,
  W_VALUE: 0.3,
  TASTE_HALFLIFE_DAYS: 60,
  COLD_START_TASTE: 0.7,
  IMPLICIT_CLICKED: 0.65,
  IMPLICIT_SWAPPED: 0.2,
  IMPLICIT_NO_ACTION: 0.45,
  RATING_VALUES: { good: 1.0, ok: 0.5, bad: 0.0, skipped: 0.4 },
  FATIGUE_TAU_DISH: 7,
  FATIGUE_TAU_SHOP: 3,
  FATIGUE_TAU_TAG: 2,
  FATIGUE_MAX_SHOP_PENALTY: 0.5,
  FATIGUE_MAX_TAG_PENALTY: 0.3,
  FATIGUE_FLOOR: 0.02,
  JITTER_MIN: 0.85,
  JITTER_MAX: 1.15,
  MAX_SWAPS: 2,
};
```

### 6.8 推荐理由

取对最终分贡献最突出的因子，套用模板生成一句话：

| 条件 | 文案 |
|---|---|
| 无 observation（冷启动） | 还没试过，试试看 |
| 最近一次 `rated` 为 `good` | 你上次说好吃 |
| `taste` 在候选集中最高且无上条 | 评价一直不错 |
| `value` 在候选集中最高 | 同类里最便宜 |
| `f_dish ≥ 0.85`（约 14 天以上没吃这道菜）且无上条 | 好久没吃了 |
| 以上都不满足 | 换换口味 |

按表格顺序取第一个命中的。带理由的推荐更容易被接受，能实际压低「换一个」的点击率 —— 这不是装饰。

## 7. 界面与交互流

两个页面加一个浮层。

### 7.1 「今天这顿」

入口 URL：`/?slot=lunch`。未带 `slot` 参数时按当前时间推断：10:30 前为 `breakfast`，15:00 前为 `lunch`，之后为 `dinner`。

内容是一张卡片：菜名（大字）、店名、参考价、一句推荐理由。

- **[去下单]** —— 主按钮。写入 `clicked` 事件，然后打开店铺链接。
- **[换一个]** —— 右上角小字，视觉上不鼓励点击。写入 `swapped` 事件，将该 `dishId` 加入 `excludedDishIds` 后重新调用 `recommend`。累计 2 次后按钮消失。
- 底部一个不起眼的入口通向候选池。

若过滤后无可推荐项，卡片位置显示引导文案与候选池入口。

### 7.2 「候选池」

按店分组的列表。

- 加店：名字、平台、粘贴链接、卫生标记
- 加菜：菜名、参考价、适用饭点（多选）、tags
- 顶部：导出 JSON / 导入 JSON
- 每道菜旁显示其**当前 `taste` 值与被吃过的次数**

最后一条是刻意设计：让用户看得见系统在学什么。当推荐开始变得奇怪时，能直接定位是哪条数据歪了，而不是对着黑盒猜测。

- 每道菜旁另有「链接失效了？」入口，一键跳到该店的链接编辑框

### 7.3 反馈浮层

**时机是下一顿打开时，补问上一顿。** 用户刚点完「去下单」返回页面时**不问** —— 那时饭还没吃。

判定条件：取时间上最近的一个 observation，若它**不属于「当前本地日期 + 当前 slot」**且没有 `rated` 事件，则弹出浮层询问它。每次最多问一个 —— 积压再多也只补问最近那顿，避免一次弹出一串问题。

```
上顿的黄焖鸡怎么样？　[好吃] [还行] [不了] [没吃成]
```

四个大按钮，点任意一个即写入 `rated` 事件并关闭浮层。目标是**一次点击结束**。

下方一行小字，均为选填：

- **[吃坏了]** —— 写入 `sick` 事件，同时将该店 `hygiene` 置为 `blocked`，不作二次确认
- **[填实付价]** —— 展开一个数字输入框，写入 `paid` 事件

## 8. 外部集成

### 8.1 跳转链接

**不逆向、不构造 URL scheme、不猜商品页 URL 结构** —— 那些一旦平台改版即全部失效。

做法：用户在美团/饿了么 App 内点「分享」，得到一条 H5 短链（形如 `dpurl.cn/...` 或 `t.elema.cn/...`），粘贴进候选池。iOS Safari 打开这类链接会自动唤起对应 App 的店铺页。零逆向、零反爬对抗、完全合规。

代价：录入每家店时多一次「分享 → 复制」动作，一次性成本。

**兜底**：[去下单] 旁常驻一个「复制店名」按钮。若链接未能唤起 App，用户可复制店名自行搜索。这条路径必须存在 —— 链接失效那天用户正饿着。

### 8.2 快捷指令（手工配置，非代码）

在 iOS「快捷指令 → 自动化 → 个人自动化 → 特定时间」建三条，动作选「打开 URL」，均设为**运行前不询问**：

| 时间 | URL |
|---|---|
| 08:00 | `https://<用户名>.github.io/meal/?slot=breakfast` |
| 11:30 | `https://<用户名>.github.io/meal/?slot=lunch` |
| 17:30 | `https://<用户名>.github.io/meal/?slot=dinner` |

时间由用户按自己作息设定。此步骤需在 README 中写出图文步骤。

### 8.3 部署

GitHub Pages，仓库路径 `/meal/`。需包含 `manifest.json`（`display: standalone`、图标、`name`、`short_name`）与 `apple-mobile-web-app-capable` meta 标签。

## 9. 测试策略

### 9.1 自动化测试

`recommender` 为纯函数、零依赖，用 Node 自带的 `node:test` 运行，不引入任何测试框架。必须覆盖：

- 空候选池 → 返回 `null`
- 全部店铺被拉黑 → 返回 `null`
- 零事件冷启动 → 所有菜 `taste` 均为 0.7，不崩溃
- 连续换两次后仍能给出第三个不同的推荐
- 昨天刚吃过的菜排序明显靠后
- 候选集只有一道菜时价格百分位不崩（`value = 0.5`）
- 事件流归约优先级：同一顿内 `rated` 覆盖 `clicked`
- `skipped` 被正确记为 0.4 而非 0.65
- 时间加权：60 天前的 `good` 权重恰为近期 `good` 的一半

`store` 必须测**导出 → 导入的往返一致性**（深比较相等）。这是用户唯一的备份手段，必须可靠。

测试中需注入固定的 `now` 与可替换的随机源，使 `jitter` 在测试下可确定。

### 9.2 iPhone 手工验收清单

自动化无法覆盖，需在真机逐条确认：

1. 添加到主屏后能以独立窗口打开（无 Safari 地址栏）
2. 三条快捷指令自动化到点真的会弹出对应饭点的页面
3. 点 [去下单] 真的唤起美团/饿了么 App 并落在正确店铺页
4. **杀掉 Safari 并重启手机后，候选池与历史数据仍在** —— 直接验证 ITP 豁免是否如预期生效
5. 导出 JSON 能存入「文件」App，再导入后数据完整

## 10. 已知风险与未决问题

| 风险 | 影响 | 应对 |
|---|---|---|
| **外卖平台分享短链可能有有效期**。设计阶段无法确认，需实际使用中观察 | 链接失效则无法跳转 | 候选池提供「链接失效了？」重录入口；卡片上常驻「复制店名」兜底。若短链不过期，代价仅是两个不常用按钮 |
| 快捷指令强行打开网页比通知更打断人 | 用户可能关闭自动化 | 若实际使用中难以忍受，升级为「轻后端 + Bark 推送」；数据模型与推荐逻辑不变，仅需替换存储层 |
| 无 Service Worker，弱网时打不开 | 饭点偶尔无法使用 | v1 接受。已有「复制店名」兜底但需先打开页面；若成为实际痛点再评估加 SW |
| 冷启动需手动录入 20–30 家店 | 用户可能在录入阶段放弃 | 候选池支持增量添加，5 家店即可开始使用；乐观初始化保证新录入的菜会被优先试推 |
| 数据仅存单台设备 | 换手机或清数据即丢失 | 一键导出 JSON；README 中建议每月导出一次至「文件」App |

## 11. 后续版本可能方向

以下均不在 v1 范围，仅作记录，避免 v1 过度设计：
