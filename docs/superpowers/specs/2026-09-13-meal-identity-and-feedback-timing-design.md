# 「这一顿」的身份与补问时机

> 这是对两份现行 spec 的修订：
> - `2026-08-26-browse-and-implicit-signals-design.md`（下称「08-26 spec」）的 §6「归约规则变更」
> - `2026-08-22-meal-recommender-design.md`（下称「原 spec」）的 §7.3「反馈浮层」中「何时补问」的部分
>
> 两份 spec 中未被本文提及的部分继续有效。

日期：2026-09-13

## 1. 起因

v1 上线后，重放真实备份与构造场景时发现两个根因不同的问题。

### 1.1 R1：这一顿属于**哪天**，是从写入时刻推出来的

事件分组键是 `localDateKey(e.ts) | slot | dishId`。`slot` 由页面写入时带上，是记录下来的；**日期却是从写入那一刻推出来的**。

**场景 B（跨零点下单）**：

```
23:55 打开，推荐 A → 划到 B → 00:05 点「去下单」
```

`recordOrder` 补写的 `recommended` 与 `clicked` 用的是写入时刻 00:05，于是：

```
观察值：09-11 晚餐 A，无动作        ← 幽灵记录，之后会被补问「上顿的 A 怎么样」
观察值：09-12 晚餐 B，已下单        ← 日期错成第二天
09-12 晚餐打开：卡片已被预先定在 B 上，理由还是昨晚那句
```

### 1.2 R2：哪一顿算**当前这顿**，只看时钟落在哪个饭点

一顿外卖从下单、送达到吃完要半小时到一小时，而饭点边界（10:30、15:00、午夜）是一条死线。

**场景 A（饭点边界前下单）**：

```
10:25 早餐下单「汉堡」
10:35 重新打开 App
```

`ui-today.js` 启动时先 `renderFeedback()` 后 `render()`。10:35 已是午餐，早餐不再算「当前这顿」，于是：

- 浮层立刻补问「上顿的汉堡怎么样？」—— **下单才 10 分钟，外卖可能还没到**。浮层没有关闭出口，只能随手答一个，多半是「没吃成」，0.4 进入口味模型
- 卡片切到午餐推荐，并写下一条午餐 `recommended`

> 更正（2026-09-13）：此前 TODO 里把场景 A 描述为「已下单那顿永远不被补问」，
> 用纯函数重放后确认是**补问得太早**。「永远问不到」是只做推迟、不改挑选规则时
> 才会出现的后果，见 §4.1。

### 1.3 为什么是两个根因

把「这一顿的日期」记进事件（§3）只能修 R1。R2 是产品问题：何时算「这顿过去了」。

## 2. 决策

| | 决策 | 由谁定 |
|---|---|---|
| R1 | 把日期显式记进 `recommended` / `clicked`，归约优先用它，没有则退回推算 | 设计讨论中同意 |
| R2 | **只推迟补问，卡片照切**：过了饭点边界，卡片照样切到新饭点；已下单的那顿满 `FEEDBACK_DELAY_MINUTES` 才补问 | 用户在两种方案中选定 |
| R2 附带 | 补问优先挑「最近下过单、还没评分」的那一顿 | 由上一条推出的必然结果，见 §4.1 |

### 2.1 否决的方案

- **写入时把 `ts` 伪造成渲染那天的 23:59:59**：`ts` 是真实时间，推迟补问要从真实下单时刻起算，伪造后会算错。
- **点下单时发现日期变了就重新渲染**：v1 最终评审曾提出，会把轮播从用户手指底下重置，比 bug 本身更难受。
- **不写没下单那顿的 `recommended`**：刷新会重新掷骰子，推翻 08-26 spec §4.2。
- **下单后保留卡片 N 小时**（R2 的另一个选项）：用户未选。
- **没点过下单的那顿不再补问**：真实备份里 3 条这种评分有 1 条是「还行」，并非全是无效问题；且与本次问题无关，不混入。

## 3. R1：记录这一顿的日期

### 3.1 数据字段（改写原 spec §5.3、08-26 spec §5）

`recommended` 与 `clicked` 增加**可选**字段 `dateKey`：`'YYYY-MM-DD'`，表示这条事件属于哪一天的那一顿，与观察值的 `dateKey` 同格式。

| `type` | 是否带 `dateKey` | 理由 |
|---|---|---|
| `recommended`、`clicked` | **带** | 描述的就是「当前这一顿」 |
| `rated` / `paid` / `sick` | 不带 | 已由 `targetTs` 精确回指某一组 |
| `muted` | 不带 | 表态针对菜，不属于任何一顿 |

**不迁移数据**：事件日志只追加不修改，老事件与导入的旧快照永远没有 `dateKey`，一律退回 `localDateKey(e.ts)`，行为与现在完全一致。`fromSnapshot` 不校验事件字段，无需改动；`SNAPSHOT_VERSION` 不升。

`store.appendEvent` 增加参数 `dateKey = null`，写法同 `targetTs`：非空才写入事件。

### 3.2 归约（改写 08-26 spec §6）

**Pass 1 分组**：

```
dateKey = e.dateKey ?? localDateKey(e.ts)
分组键  = dateKey | slot | dishId
```

**Pass 2 挂反应事件**，判断顺序由两层变为三层：

```
1. 有 targetTs → 找 ts 相等的那组                    （rated / paid / sick，不变）
2. 有 dateKey  → 找 dateKey|slot|dishId 这一组          （clicked，新增）
3. 都没有，或指向的组不存在 → 同 slot|dish 中 ts 最大且 <= e.ts 的组（老事件，不变）
```

第 2 层在场景 B 中并非必需（启发式碰巧能找对），但有字段就直接用，才不会再次依赖写入先后。

**`latestPerMeal`**、腻味系数、「吃过 N 次」都读观察值上的 `dateKey`，随 Pass 1 自动修正，无需单独改动。

**`currentPick(events, slot, nowKey)`**：判断一条 `recommended` 是否属于今天时，同样用 `e.dateKey ?? localDateKey(e.ts)`。

**`buildMutedIndex`** 不改：静音日期仍从 `ts` 推算（§3.1）。

### 3.3 观察值新增 `clickedTs`

组内最后一次 `clicked` 的 `ts`，无则为 `null`。供 §4 计算推迟时长 —— 观察值的 `ts` 是推荐时刻，不是下单时刻。

### 3.4 场景 B 修正后

```
23:55 推荐 A（dateKey 09-11）→ 划到 B → 00:05 点下单
      补写 recommended B（dateKey 09-11）+ clicked B（dateKey 09-11）

观察值：09-11 晚餐 B，已下单     ← 唯一一条
09-12 晚餐打开：未被预先定下，正常推荐
```

A 的幽灵记录一并消失：同一顿里 B 的推荐更晚，`latestPerMeal` 只保留 B。

## 4. R2：补问挑哪一顿、何时问（改写原 spec §7.3 的补问时机）

### 4.1 为什么光推迟不够

补问目前只看**最近一条**观察值。若只加推迟：

```
10:35 打开 → 早餐推迟不问 → 卡片切到午餐，写下午餐 recommended（没点）
12:30 打开 → 最近一条是「今天午餐」，属当前这顿 → 不问
18:00 打开 → 最近一条是那条没点过的午餐 → 问午餐，早餐被永久跳过
```

所以挑选规则必须同时改。

### 4.2 新常数

`src/config.js`：`FEEDBACK_DELAY_MINUTES: 120` —— 下单后多久才补问这一顿。

分钟到毫秒的换算属于单位换算，按 CLAUDE.md 留在 `observations.js` 内。

### 4.3 两个函数

**`feedbackCandidate(observations, nowTs, slot)`** —— 挑出「该问的那一顿」，**不管推迟是否到期**：

```
nowKey    = localDateKey(nowTs)
isCurrent = o.dateKey === nowKey && o.slot === slot
lastRated = source === 'rated' 的观察值中 ts 最大者（无则不设下限）

候选 = 满足全部条件的观察值：
  · source === 'clicked'        （点过下单、没评分）
  · !isCurrent
  · 若有 lastRated：o.ts > lastRated.ts

有候选 → 返回 ts 最大的那条
无候选 → 旧规则：取 ts 最大的观察值 latest；
         isCurrent(latest) 或 latest.source === 'rated' → null；否则 latest
```

**`pendingFeedback(observations, nowTs, slot)`**（签名不变）：

```
c = feedbackCandidate(...)
c 为 null                                         → null
c.source === 'clicked' 且 nowTs - c.clickedTs < 推迟 → null
否则                                               → c
```

**推迟期间不退回旧规则、不拿别的记录顶上。** 若改问一顿没下单的，用户随手答了，它就成了 `lastRated`，真正下过单的那顿因早于它而被排除，从此问不到。

`>=` 推迟时长即补问（正好 120 分钟时问）。

仍然**每次最多返回一条**；早于 `lastRated` 的积压不追问，与原设计一致。

### 4.4 调用方

| 调用处 | 用哪个 | 理由 |
|---|---|---|
| `renderFeedback()`（补问浮层） | `pendingFeedback` | 推迟期间不弹 |
| `render()` 里第 9 条的守卫（被补问的菜不排开场位） | **`feedbackCandidate`** | 见下 |

守卫若仍用 `pendingFeedback`，推迟期间会失效：

```
14:50 午餐下单「骨汤猪肚鸡」（午晚都可推）
15:10 晚餐打开 → 推迟中 → 守卫不生效
      它点过没评分，不算「吃过」，无腻味扣分 → 很可能又排第一
```

改用 `feedbackCandidate` 后，**刚下单的菜在推迟期间同样不排第一**，仍留在轮播里划得到。

### 4.5 走一遍

**场景 A**

```
10:25 早餐下单「汉堡」
10:35 打开（午餐）→ 候选=汉堡，10 分钟 → 不补问
      卡片切到午餐；汉堡若排第一则顺延到第二位
      写下午餐 recommended（没点）
12:30 打开 → 候选仍是汉堡（没点的午餐不是候选），满 2 小时 → 补问汉堡 ✓
```

**连着下两顿**

```
10:25 早餐下单 → 11:00 午餐下单
13:00 打开（午餐）→ 午餐是当前这顿、非候选 → 候选=早餐，满 2 小时 → 问早餐
      答完，早餐成为 lastRated
15:30 打开（晚餐）→ 候选=午餐（晚于早餐），满 2 小时 → 问午餐 ✓
```

**久远的未评分下单**

```
三天前点过下单未评分，其后评过别的顿
→ 早于 lastRated，不是候选，不被翻出来追问 ✓
```

## 5. `ui-today.js` 改动

- `render(now = Date.now())` 与 `renderFeedback(now = Date.now())` 接收 `now`。**启动时只读一次时钟**，两者共用；评分后重渲染与「重试」照旧各自取当下时刻
- `state` 增加 `dateKey`（渲染时的 `localDateKey(now)`），与 `slot` 并列
- 首次写 `recommended`、`recordOrder` 补写 `recommended` 与写 `clicked`，均带上 `dateKey`。`recordOrder` 已是先快照 `state` 再使用，`dateKey` 一并纳入快照
- 第 9 条守卫改调 `feedbackCandidate`

## 6. 测试策略

### 6.1 自动化（`test/observations.test.js`）

**每条都必须具备判别力** —— 拿改动前的代码跑必须失败。这是 2026-09-11 查真实备份时学到的：九条带 `targetTs` 的事件里判别性事件 0 条，「字段写进去了」不等于「它在起作用」。

R1：

1. 带 `dateKey` 的 `recommended` 按 `dateKey` 分组而非 `ts`（00:05 写入、`dateKey` 为前一天 → 归前一天）
2. 带 `dateKey` 的 `clicked` 精确挂到对应组 —— 构造启发式会挂错的局面：同 slot|dish 两组，另一组 `ts` 更接近点击时刻
3. 场景 B 端到端：唯一观察值为「09-11 晚餐 B，clicked」，无 09-12 记录、无 A 的幽灵
4. `currentPick` 认 `dateKey`：09-12 晚餐未被定下；09-11 晚餐定下的是 B
5. `clickedTs` 为组内最后一次点击时刻；无点击为 `null`

R2：

6. 下单 10 分钟且已换饭点：`pendingFeedback` 为 `null`，`feedbackCandidate` 返回该顿
7. 边界：恰好 `CONFIG.FEEDBACK_DELAY_MINUTES` 分钟时返回该顿（测试读 `CONFIG`，不写死 120）
8. 场景 A：其后有一条无动作的午餐记录，推迟期满后问的仍是早餐
9. 推迟期间不退回旧规则去问那条无动作记录
10. 早于 `lastRated` 的已下单记录不是候选，退回旧规则
11. 当前这顿已下单时不是候选；更早一顿已下单的照样问
12. 连着下两顿：先问早餐，评完再问午餐

回归：现有 131 条测试不改动、全部通过。老事件无 `dateKey` 时行为不变，由现有测试保证。

### 6.2 浏览器实测

向本地库写入构造事件后检查：首次 `recommended` 带 `dateKey`；点下单写入的两条事件都带 `dateKey`；10 分钟前在别的饭点下过单时，不弹补问，且该菜不在开场位。

### 6.3 真机验收清单新增

- **21.** 饭点边界前下单，2 小时内重开：卡片切到新饭点、不弹补问、刚下单的菜不在第一位；满 2 小时后打开补问那一顿。日常使用即可遇到，用备份 + 脚本核对
- **22.** 跨零点下单（23:5x 打开、0 点后点下单）：次日同饭点不被预先定下；备份中该组 `dateKey` 为前一天。**需熬夜，列为可选**，遇到再验

## 7. 明确不做

- 没点过下单的那顿照样补问（§2.1）
- 过了饭点边界，卡片照样切换，包括评分后当场切换（§2）
- 补问每次仍最多一条
- 不迁移老数据、不升 `SNAPSHOT_VERSION`、静音日期推算不改、候选池页面不动
