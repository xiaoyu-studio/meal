# 「别再推这个」的撤销出口

> 这是对 `2026-08-26-browse-and-implicit-signals-design.md`（下称「08-26 spec」）的一次增补。
> 它新增 `unmuted` 事件，改写 08-26 spec §7.2 里「最近一次 `muted` 事件」的含义。
> 08-26 spec 中未被本文提及的部分继续有效。

日期：2026-09-14

## 1. 起因

「别再推这个」是全应用唯一按下去就留下持久后果、却没有撤销出口的按钮，而且紧挨着「复制店名」。

2026-09-10 做过止血（`5cdf56d`）：候选池菜品行显示「已静音 · MM-DD」，至少让人知道是哪道菜被按过。
但**改不回来**：误触之后只能等它按 `MUTE_TAU_DAYS` 自然回升；再按一次只会把时钟重新拨满。

另一种情况同样没有出口：当时确实不想吃，过几天又想吃了。

## 2. 决策

| | 决策 | 由谁定 |
|---|---|---|
| 场景 | **候选池里随时取消**：不管多久以前按的，点了就回到没静音过的状态 | 用户在三个场景中选定（另两个：只在卡片上当场撤销；两个都要） |
| 机制 | 新增 `unmuted` 事件，归约时比较先后（方案 A） | 用户同意 |
| 取消的效果 | 立刻恢复到从没静音过的排序，不是从压低处慢慢回升 | 设计讨论中同意 |

### 2.1 否决的方案

- **把「是否静音」存成菜品上的可变字段**（方案 B）：违反「事件日志只追加、观察值现算」，旧 `muted` 事件还得迁移。
- **新增 `unmuted`，但按本地日期比较先后**（方案 C）：同一天先静音后取消，两者日期相同分不出先后，只能硬规定顺序。
- **只在卡片上当场撤销**（按完后 toast 里几秒的「撤销」按钮）：只防误触，覆盖不了「过几天又想吃了」；用户未选。
- **取消前弹确认框**：「删」有确认框是因为不可逆；取消静音误点的后果只是这道菜照常出现，下次划到再按一次「别再推这个」就回来了。

## 3. 事件与归约

### 3.1 新事件

```js
{ id, ts, slot: null, dishId, type: 'unmuted', value: null }
```

写入走现有的 `appendEvent({ slot: null, dishId, type: 'unmuted' })`，`store.js` 不改。

**`slot` 为 `null` 是有意的。** `reduceObservations` 的 Pass 2 会把所有非 `recommended` 事件按
`slot|dishId` 找组挂上去（现有的 `muted` 带着按下时的饭点，就被挂上去了，只是归约不认这个类型）。
候选池页面没有「当前饭点」，`slot: null` 让它匹配不到任何组，在 Pass 2 开头就被跳过。

### 3.2 `buildMutedIndex(events)` 的新规则

纯函数，签名与返回形状不变：`Map<dishId, 最近一次静音的本地日期键>`。

对每道菜：

1. 取 `ts` 最大的 `muted` 事件，记为 M；取 `ts` 最大的 `unmuted` 事件，记为 U
2. 没有 M → 不在结果里
3. 有 U 且 `U.ts >= M.ts` → 不在结果里（已取消）
4. 否则 → `localDateKey(M.ts)`，与现在一致

| 事件序列 | 结果 |
|---|---|
| 09-01 静音 | `09-01` |
| 09-01 静音 → 09-05 取消 | 不在结果里 |
| 09-01 静音 → 09-05 取消 → 09-10 静音 | `09-10`，力度从 09-10 重新衰减 |
| 09-01 取消 → 09-05 静音 | `09-05` |
| 只有取消，没有静音 | 不在结果里 |

第 3 步用 `>=`：两条事件 `ts` 恰好相等时算已取消。实际不会发生，写明是为了规则无歧义。

先后用 `ts` 比较；静音力度仍按 08-26 spec §7.2，从 M 那天的本地日期起算天数。

### 3.3 不改的地方

- `muteOf`、`rankCandidates`：它们拿到的已经是「没被取消的静音」
- `reduceObservations`：`slot: null` 的事件匹配不到任何组
- `snapshot.js`：导入不校验事件类型；老备份没有 `unmuted`，行为不变。**不升 `SNAPSHOT_VERSION`**
- 今天这顿页面（`ui-today.js`、`index.html`）：不改。卡片已经打开时，取消静音下次加载才影响排序 ——
  与「静音下次加载才生效」同一条规矩（08-26 spec §4.1、§4.3）

## 4. 候选池界面

### 4.1 按钮位置

「取消」放进已有的「已静音 · MM-DD」那一行，紧跟日期：

```
红烧牛肉面　¥28・午/晚
已静音 · 09-11  取消
                                好吃度 0.62・吃过 3 次  删
```

```js
`<span class="dish-muted">已静音 · ${esc(mutedKey.slice(5))}` +
`<button class="link" data-unmute-dish="${esc(d.id)}" type="button">取消</button></span>`
```

`data-unmute-dish` 的属性值必须过 `esc()`（CLAUDE.md 安全规则）。

不放右栏：右栏 `.dish-stat` 是 `white-space: nowrap`，375px 下再塞一个按钮会把左栏菜名挤没；
而且与「删」挨在一起容易点错。

### 4.2 样式

沿用 `.link`（灰色下划线，与「删」「跳转链接」一致），只加一条：

```css
.dish-muted .link { font-size: inherit; padding: 0 0 0 0.4rem; }
```

`.dish-muted` 本就独占一行（`display: block`），估算「已静音 · 09-11 取消」放得进 375px 下 126px 的左栏。
**真机 PingFang SC 渲染与桌面不同，第 15 条「手机宽度布局」必须重验。**

### 4.3 点击之后

在 `#shops` 已有的事件委托里新增一个分支：

1. `appendEvent({ slot: null, dishId, type: 'unmuted' })`
2. `render()` —— 那一行消失
3. 底部 toast：`已取消静音「<菜名>」`，菜名从 `loadAll()` 取，取不到时显示「已取消静音」。
   `showToast` 走 `textContent`，菜名不需要额外转义

与「删菜」分支同一个写法（先查名字、再写、再渲染、再 toast）。

**写入失败**：落到已有的 `catch`，顶部 `#io-msg` 显示「操作失败，请稍后重试。」。
「已静音」那一行不会消失，没看到顶部提示也能看出没生效。

## 5. 测试

### 5.1 自动化

`test/observations.test.js`，`buildMutedIndex` 新增 6 条：

| # | 事件序列 | 期望 | 旧代码 |
|---|---|---|---|
| 1 | 09-01 静音 → 09-05 取消 | 不在结果里 | 必须失败 |
| 2 | 静音与取消 `ts` 相等 | 不在结果里 | 必须失败 |
| 3 | 甲、乙都静音，只取消甲 | 甲不在；乙仍为原日期 | 必须失败 |
| 4 | 静音 → 取消 → 09-10 再静音 | `09-10` | 通过（预期） |
| 5 | 09-01 取消 → 09-05 静音 | `09-05` | 通过（预期） |
| 6 | 只有取消，没有静音 | 不在结果里 | 通过（预期） |

第 4–6 条在旧代码上通过是预期的：它们防新规则的错误实现（「有取消就永远不算静音」「取消抵消了之后的静音」）。

- 7. `slot: null` 的 `unmuted` 不影响 `reduceObservations` —— 加不加这条事件，输出深度相等。旧代码上通过（预期），钉住 §3.1 的前提。

`test/recommender.test.js` 新增 1 条（端到端）：

- 8. 一道菜先 `muted` 后 `unmuted`，`rankCandidates` 的输出（顺序与分数）与完全没有这两条事件时深度相等，注入同一个 `random`。旧代码上必须失败。
