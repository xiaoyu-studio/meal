# 浏览式选菜与隐式信号重设计

> 这是对 `2026-08-22-meal-recommender-design.md`（下称「原 spec」）的一次修订。
> 它推翻原 spec 的 §3.6，并改写 §5.3、§6.2、§6.3、§6.5、§7.1。
> 原 spec 中未被本文提及的部分继续有效。

日期：2026-08-26

## 1. 起因

真机验收期间用出来的三个问题：

1. **「换一个」上限 2 次，用满后按钮消失**，不解释也没出路。用户想再看看时被卡住。
2. **换掉的菜进入排除列表，这一顿再也见不到**。看了一圈想回头选最初那道，没有退路。
3. **「换一个」一律记 0.2 负反馈**。但用户左右翻看常常只是想知道今天有哪些选择，不是嫌弃当前这道。把「浏览」当成「拒绝」记账，会让好奇心持续污染口味数据。

顺带解决的还有一个：点「去下单」跳去外卖 App 再切回来时，页面重载后推荐理由被替换成「这顿已经定了」，看起来像是这一顿被锁死了。

## 2. 推翻了什么

原 spec §3.6 原文：

> 一顿一个推荐，配一个「换一个」按钮，上限 2 次，用满后按钮消失。被换掉的选项计为负反馈。

**本次推翻「上限 2 次」与「计为负反馈」两个条款，保留「一顿一个推荐」。**

§3.6 的论据是「给三个并排选择只是把纠结从 50 个店缩小到 3 个，没有真正消除它」。这个论据反对的是**同屏并排比较**。左右滑动的轮播始终只显示一道菜，无法把两道菜摆在一起比，因此该论据未被推翻 —— 被推翻的只是它附带的次数限制。

## 3. 决策

### 3.1 「换一个」变为浏览

左右滑动在今天这一顿的候选中循环切换，**无次数上限**。

**理由**：翻看候选与拒绝当前项是两种不同意图，用同一个动作表达必然有一方失真。既然形态上仍是一次一道菜，纠结的成本主要来自并排比较，而非翻看本身。

### 3.2 浏览不产生任何评分影响

划过的菜不计分、不留观察值，就像从未出现过。下一顿照常可能推荐它。

**理由**：用户明确表示「左右划就是想看看有哪些推荐的」。任何自动归因（哪怕只是轻微降权）都会把好奇心记成厌恶。

**代价**：一道每次都被划过、从不被选中的菜，其分数永不变化，会长期占据靠前位置。这个代价由 §3.3 的手动出口承担，系统不做猜测。

### 3.3 新增「别再推这个」，机制为降权而非排除

按下后该菜分数被大幅压低，随时间自行回升。

**权衡记录**：设计讨论中曾建议改为硬性排除 N 天（走原 spec §6.1 硬过滤层），理由是降权不保证生效 —— 候选池小时，被压低的菜仍可能排在最前，按钮显得失灵。用户选择了降权方案。**该风险已知且被接受**：若真机使用中发现按钮「按了没用」，应回到本节重新评估硬排除。

采用降权的好处是「隔一段时间自己回来」不必另造机制，指数回升是现成的形状，与 §6.5 的疲劳系数一致。

### 3.4 「无动作」不再计分，但保留记录

一顿推了、既没点也没打分的饭，**仍然产生观察值，但该观察值不带数值**，不参与口味计算。

**理由**：切出应用可能只是去回一条微信或被别的事打断，与这道菜好不好吃无关。

**为什么不直接丢弃这条观察值**：`pendingFeedback` 从观察值中挑选「下次该补问哪一顿」。不产生观察值就永远不会被补问，而「推了但没动作」恰恰是最需要补问的情形 —— 用户可能真吃了只是忘了打分，也可能想说「没吃成」。补问机制本就是为「会忘记打分」而建，丢弃观察值等于堵死它自己的入口。

原 spec §5.3 中「『推了但既没点也没换』本身就是一条可分析的记录」这句话依然成立，只是该记录不再折算成分数。

### 3.5 `clicked` 保留 0.65

**理由**：它与前两者性质不同 —— 那是用户主动按下的按钮，不是「什么都没发生」。且原 spec 已为它配好纠错出口：`skipped`（没吃成）记 0.4，专门用于修正「点了跳转但没真吃」。

### 3.6 旧 `swapped` 事件按「无动作」处理

改动后不再写入 `swapped`。库中已有的旧事件在归约时**一律忽略**，等同于该组没有任何反应事件。

**代价**：那些记录反映的是当时真实的拒绝意图，就此作废。用户判断其价值低于代码简洁性（这些事件全部产生于测试期，量很小）。

**连带影响**：`pendingFeedback` 原本跳过 `swapped` 的观察值不予补问。该分支一并删除，因此少量旧的「换掉过」的饭可能会被补问一次。由于每次最多补问最近一顿，影响至多一条。

### 3.7 浏览位置只在「决定」时留痕

初次展示写一条 `recommended`；浏览过程不写任何事件；只有在按「去下单」或打分时，若当前这道菜与已记录的不是同一道，才补写一条 `recommended`。

**效果**：点「去下单」跳走再切回来，看到的是你下单的那道菜与它原本的推荐理由，可以继续左右浏览 —— 与没点过时完全一致。

**已知取舍**：纯浏览到第三道、未下单就关闭应用，再次打开时回到系统最初推荐的那道，而非第三道。

**为什么接受**：让位置跨重启需要防抖写入（否则快速划过三十道菜就写三十条记录，事件流被浏览撑大，而 `reduceObservations` 每次读取都要遍历全部历史），且很可能需要新增一种事件类型（若复用 `recommended` 记录位置，纯浏览后关闭会让最后停留的那道菜领到一条观察值，与 §3.2 冲突）。用户未提出跨重启记忆的需求，故不预先支付这些代价。**若日后需要，可在本设计之上叠加，无需推翻任何部分。**

### 3.8 本轮不做「彻底拉黑」

讨论中曾设想两级：暂时雪藏（自动回归）与彻底拉黑（永久，需手动恢复）。**本轮只做前者。**

**理由**：候选池现有的「删菜」已能达成「永不再现」。两者唯一差别是删菜会连带丢失该菜的历史记录，而对一道决定永不再吃的菜，这点历史不足以换取一个新字段、一个开关和一套渲染。

日后需要时可独立添加，不影响本设计任何部分。

## 4. 交互（改写原 spec §7.1）

推荐卡片一次仍只显示一道菜。

| 元素 | 行为 |
|---|---|
| 左右滑动 | 在今天这一顿的候选中循环切换。主路径 |
| 「换一个」按钮 | 保留，语义改为「下一个」。负责发现性，以及滑动失灵时的兜底。**不再有次数上限，不再隐藏** |
| 「去下单」 | 不变。写 `clicked`；若当前菜与已记录的不同，先补写 `recommended` |
| 「别再推这个」 | **新增**。次要按钮，与「复制店名」并排，不与「去下单」争夺视觉重量 |
| 推荐理由 | 显示事件中存下的原文，不再出现「这顿已经定了」 |

### 4.1 轮播的内容与顺序

- 内容：该 slot 通过硬过滤（原 spec §6.1）的**全部**菜品
- 顺序：按最终评分降序，首尾相接循环
- **排序在页面加载时计算一次，浏览期间不重算** —— 否则划动过程中顺序变化会令人困惑
- 初始位置：排序后的第一道。若该菜正是反馈浮层当前补问的那道，则顺延至下一道（沿用原有规则）；候选只剩它一道时不顺延
- 候选池为空时维持现有空态

### 4.2 `recommended` 的写入时机

页面渲染这一顿时，若该本地日期 + `slot` 下**尚无任何 `recommended` 事件**，写入一条，`dishId` 为初始位置那道菜，`value` 为它的推荐理由。已有则不写 —— 这保证了刷新不会重新掷骰子，也保证纯浏览不产生写入。

补写只发生在按「去下单」或打分时，且仅当当前这道菜与该顿最后一条 `recommended` 的 `dishId` 不同。

### 4.3 按下「别再推这个」之后

- 写入一条 `muted` 事件，`dishId` 为当前这道菜
- **卡片自动前进到轮播的下一道**，否则用户会盯着一道刚被自己静音的菜
- **该菜仍留在本次轮播中**（排序已在加载时算定，不重排）。静音下一次加载才生效 —— 这是「顺序不中途变化」的必然结果，可接受
- **不改动这一顿已写入的 `recommended`**。若被静音的正是该顿已记录的那道菜，观察值维持不变；用户之后仍会被补问它，可答「没吃成」。不为此增加额外机制

## 5. 数据模型变更（改写原 spec §5.3）

| `type` | `value` | 变更 |
|---|---|---|
| `recommended` | **string（推荐理由）** | 原为 `null`。§5.3 的 `value` 本就允许字符串，无需改类型定义 |
| `swapped` | — | **不再写入**。归约忽略；类型定义保留以便读懂历史数据 |
| `muted` | `null` | **新增**，按「别再推这个」时写入 |
| `clicked` / `rated` / `paid` / `sick` | 不变 | |

不需要数据迁移：事件日志只追加不修改，旧事件缺少新语义时由归约规则兜底。

## 6. 归约规则变更（改写原 spec §6.2）

两处改动。

### 6.1 一顿只认最后一条推荐

同一本地日期、同一 `slot` 下若存在多条 `recommended`，**只有 `ts` 最大的那条成为观察值**，其余丢弃。

这是 §3.7 得以成立的关键：系统推了 A、用户浏览后在 B 上下单时，这一顿的观察值应当是 B。

分组与后续事件归属的其余规则（`targetTs` 精确匹配、缺失时退回启发式）不变。

### 6.2 优先级表由四行减为三行

```
1. 存在 rated   → 用其映射值（good 1.0 / ok 0.5 / bad 0.0 / skipped 0.4）
2. 否则存在 clicked → 0.65
3. 否则          → 观察值照常生成，但不带数值
```

- `swapped` 不再参与判断（§3.6）
- 第 3 行取代原来的「0.45」（§3.4）
- `rated` 的 `value` 无法识别时按第 3 行处理，即不带数值

## 7. 评分变更

### 7.1 `tasteOf`（改写原 spec §6.3）

跳过不带数值的观察值。全部观察值都不带数值时，退回冷启动值 `COLD_START_TASTE`（0.7），与没有任何观察值时一致。

### 7.2 静音系数（新增，形状对齐原 spec §6.5）

设 `d` 为距该菜最近一次 `muted` 事件的天数（自然日，设备本地时区）：

```
mute = MUTE_FLOOR + (1 - MUTE_FLOOR) · (1 - e^(-d / MUTE_TAU_DAYS))
```

- `d = 0` 时取 `MUTE_FLOOR`；`d → ∞` 时趋近 1
- 从无 `muted` 事件的菜，`mute = 1`
- 默认 `MUTE_FLOOR = 0.05`，`MUTE_TAU_DAYS = 14`

### 7.3 最终评分（改写原 spec §6.6）

```
score = (W_TASTE · taste + W_VALUE · value) · fatigue · mute · jitter
```

### 7.4 常数增删（原 spec §6.7）

| 常数 | 操作 |
|---|---|
| `IMPLICIT_SWAPPED` | 删除 |
| `IMPLICIT_NO_ACTION` | 删除 |
| `MAX_SWAPS` | 删除 |
| `MUTE_FLOOR` | 新增，0.05 |
| `MUTE_TAU_DAYS` | 新增，14 |

## 8. 明确不做

- 跨重启记住浏览位置（§3.7）
- 「彻底拉黑」二级机制（§3.8）
- 硬性排除式的「别再推」（§3.3）
- 根据划过次数自动降权 —— 这等同于把浏览记为负面信号，正是本次要消除的东西

## 9. 测试策略

`observations.js` 与 `recommender.js` 均为纯模块，以下全部由 `node --test` 覆盖：

- 同一天同一顿多条 `recommended` 时只有最后一条成为观察值
- 用户在 B 上下单时，观察值落在 B 而非系统最初推的 A
- 旧 `swapped` 事件被忽略，其所在组等同于无动作
- 不带数值的观察值不影响 `tasteOf`；全部无数值时退回冷启动
- 无动作的那顿仍能被 `pendingFeedback` 问到
- 静音系数：`d = 0` 时等于 `MUTE_FLOOR`，随天数单调回升，无 `muted` 事件时为 1
- 静音系数正确进入最终评分

**无法自动化、须进真机验收清单**：左右滑动手势本身、滑动与页面纵向滚动不冲突、「别再推这个」按下后的实际观感、下单往返后卡片与理由不变。

## 10. 对原 spec 的处理

原 spec 的 §3.6、§5.3、§6.2、§6.3、§6.5、§6.6、§6.7、§7.1 各加一条指向本文的注记，说明该节已被修订。原文保留，以便日后追溯当初为何那样设计。
