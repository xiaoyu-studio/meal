## v1 首轮（spec 2026-08-22 §9.2）

- [x] **1. 添加到主屏后能以独立窗口打开**（2026-08-26）

  Safari 打开 `https://xiaoyu-studio.github.io/meal/` → 分享 → 添加到主屏幕 →
  从主屏图标启动，确认没有 Safari 地址栏。

- [x] **2. 三条快捷指令到点真的弹出对应饭点的页面**（2026-09-08，改了做法）

  把某条自动化的时间临时改到两分钟后，锁屏等待。

  **验收中发现原配置说明是错的，README 第 4 步已重写。** 用 `https://` 地址时，
  自动化把页面开在 Safari 里 —— Safari 与主屏 App 的本地存储是**两个独立容器**，
  于是页面正常打开但候选池完全是空的。改用 `webapp://xiaoyu-studio.github.io/meal/` 后正常。

  如实记录两点：**需要解锁**才会真的进到页面；**`?slot=` 参数会被 `webapp://` 丢掉**，
  不影响使用，页面按当前时间推断饭点。

  没测出来的后果：每天自动打开的都是一个看不到自己数据、且**不受 ITP 豁免保护**的页面。

- [ ] **3. 点「去下单」真的唤起外卖 App 并落在正确店铺页** —— 推迟到有后端的版本

  淘宝闪购（原饿了么）正常。美团不行：`dpurl.cn` 短链 302 跳到 `h5.waimai.meituan.com`，
  而 iOS 的 Universal Links 跨过一次 302 就不触发，Safari 一路跟到网页版登录页。

  已修的部分（`fe552d6`）：「去下单」从 `<button>` + `location.href` 改成真实的 `<a href>`，
  淘宝闪购那条路更稳，但修不好美团（病根在 302）。

  `meituanwaimai://` scheme 已在真机验证可用，但解析短链必须有后端。原委与方案见
  spec `2026-08-22-meal-recommender-design.md` 的 §8.1 补记与 §11。**v1 期间美团走「复制店名」兜底。**

- [x] **4. 杀掉 Safari 并重启手机后，候选池与历史数据仍在**（2026-09-08）

  只验证 IndexedDB 能扛住进程被杀和系统重启，**不验证 ITP 豁免**（那是第 5 条）。

- [x] **5. 连续 7 天以上完全不打开，再打开时数据仍在**（2026-09-10）

  验证 ITP 豁免，是零后端方案成立的前提（spec §3.4）。

  没有专门安排，是开发期间自然形成的空档，事后用事件日志证实：`render()` 在这一顿没定过时
  会写一条 `recommended`，所以日志里的空洞就是没打开过。2026-09-10 的备份里：

  ```
  11.96 天　2026/8/27 22:53:16 → 2026/9/8 21:58:39　零事件
  ```

  这是整个日志里唯一超过 3 天的空档（12 天 ≈ 36 个饭点），空档之前的 17 条事件、4 道菜一条没少。
  容器也对得上：09-08 用 `webapp://` 打开数据都在，同日 Safari 容器是空的 —— 活下来的正是主屏容器。

  仍然要每月导出备份：这条证明的是 iOS 当前的豁免行为，换手机、清数据、系统策略变了仍然只有备份能救。

- [x] **6. 导出 JSON 能存入「文件」App，删掉一家店后再导入，数据完整还原**（2026-09-09）

  覆盖 spec §9.1 要求测、但零依赖约束下测不了的那段往返。判据三处：顶部「导入成功。」、
  底部 toast 的店 / 菜数量与删之前一致、**被删的那家店连同它名下的菜真的回到了页面上**（第三处才是关键）。

  **导入是整体替换不是合并** —— `importSnapshot` 先 `clear()` 店、菜、事件日志三个 store 再写入。
  验收前必须现导一份新备份，用旧备份会抹掉上次导出之后的全部改动。

## 最终代码评审后的修复

- [x] **7. 主屏图标是橙色圆环图标，不是页面截图**（2026-08-26）

  若仍是旧图标，先从主屏删除再重新添加，iOS 会缓存图标。

- [x] **8. 连着两天推到同一道菜时，第二天的评分记在昨天那顿上**（2026-09-12，依据为真机操作者报告）

  要证明的不是「`targetTs` 写进去了」，而是它在**能改变结果的时候**改变了结果：评分写入那一刻，
  同 `slot|dishId` 必须已经存在一组更新的推荐，否则退回启发式会给出同样的答案，没有判别力。
  2026-09-11 查过真实备份，九条带 `targetTs` 的事件里判别性事件 0 条，所以必须人为布置，且跨一次午夜是硬下限。

  做法：
  1. 候选池把其他店全部**拉黑**（可逆，别删菜），让某个饭点只剩一道菜（第 9 条的守卫要求 `ranked.length > 1`，此时不触发）
  2. 第一天在该饭点打开 App，点「去下单」，**不要评分**
  3. 当天别再在其他饭点打开 App —— 新的观察值会把补问对象顶掉
  4. 第二天同饭点打开，浮层问上顿怎么样，答一个评分
  5. 导出备份，检查那条 `rated` 的 `targetTs` 指向**第一天**那组

  测完把拉黑改回「未知」。第 8 条与第 9 条互斥，先做第 8 条。

- [x] **9. 补问某道菜时，这一顿不会又推同一道菜**（2026-09-13，依据为真机操作者报告）

  候选池只剩一道菜时除外。

- [x] **10. 候选池里能把「已拉黑」改回「未知 / 放心」，改完该店的菜重新出现在推荐里**（2026-09-08）

- [x] **11. 导出时切到别的 App 再切回来，页面不会卡死**（2026-08-26）

  验证事务被中断后 Promise 会落地、错误会显示出来。显示的是 `#io-msg` 的「导出失败，请稍后重试。」，
  不是 `#failure` 卡片（那是 `render()` 读失败时的兜底）。

  真实导出只要几毫秒，手动切 App 切不进竞态窗口。验收时临时提交了把导出事务撑开十秒的补丁
  （用连续 `count()` 请求保持事务打开；`setTimeout` 没用，事务没有待处理请求时会立刻自动提交），验完 revert。

## 「这一顿」的身份与补问时机（spec 2026-09-13）

- [x] **21. 饭点边界前下单，2 小时内重新打开**（2026-09-14）

  卡片切到新饭点、**不弹补问**、刚下单的那道菜不在第一位；满 2 小时后再打开，补问的是那一顿。
  核对办法：那顿 `rated` 的 `ts` 减去同组 `clicked` 的 `ts`，应不小于 `FEEDBACK_DELAY_MINUTES`（120 分钟）。
  备份里不记录浮层出现的时刻，「不弹补问」只能靠眼睛看。

  依据 `meal-2026-09-14.json`：14:30:31 午餐「汤品自选套餐」点下单（带 `dateKey`）→
  15:00:25 打开，写入晚餐推荐，**真机操作者确认没弹补问** → 16:41:24 补问并评分，回指午餐那一顿，
  距下单 130.9 分钟。用真实归约重放：下单后 119 分钟 `pendingFeedback` 为空，120 分钟起才返回那一顿；
  旧代码在 15:00:25 就会补问。

  **「不在第一位」这半没验到**：那道菜 09-11 被静音过，本来就排末位，不具判别性。
  守卫逻辑由浏览器实测与单元测试覆盖，不再专门补验。

## 删店的淡出动画（2026-09-20）

- [x] **26. 删店时卡片是淡出的，不是「啪」一下消失**（2026-09-20 记录通过，依据为真机操作者报告）

  候选池里删掉一家店（**先用一家不要的测试店**），盯着那张卡片：应该看到约 0.25 秒的淡出 +
  轻微缩小，然后列表才重排。删完 toast 照常弹出。

  另外：iOS 设置里开了「减弱动态效果」时，这里会退回瞬间消失，这是有意为之（CSS 里
